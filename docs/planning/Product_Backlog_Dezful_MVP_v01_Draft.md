# فهرست کارهای توسعه و نقشه اجرای نسخه اول

**محصول:** سامانه مدیریت ارجاع کار مجریان ذی‌صلاح، دفتر نمایندگی دزفول  
**نسخه سند:** `Product Backlog v0.1 — Draft`  
**تاریخ:** ۱۴۰۵/۰۸/۲۸ / ۲۰۲۶-۱۱-۱۹  
**وضعیت:** پیشنهاد ترتیب اجرا؛ نیازمند مرور و تصویب مالک محصول. اسناد پنج‌گانه اولیه تغییر نکرده‌اند.  
**انتخاب فنی مالک محصول:** `ASP.NET Core 11` / `net11.0`، `EF Core 11`، `React + TypeScript`، `SQL Server`، `Modular Monolith`.  

## ۱. مبنا و نحوه استفاده

این Backlog از پنج سند بازنگری‌شده زیر استخراج شده است: `Dezful_Executor_System_Decision_Register_v01.md`، `Business_Rules_Specification_Dezful_MVP_v04_Draft.md`، `Data_Dictionary_Entity_Schema_Dezful_MVP_v04_Draft.md`، `User_Flows_Wireframe_Logic_Dezful_MVP_v04_Draft.md`، `Technology_Stack_Architecture_Dezful_MVP_v04_Draft_NET11.md`. فایل‌های فوق همگی پیش‌نویس‌اند؛ شناسه‌ها در ستون ردیابی، شناسه سند پروژه هستند نه شماره مصوبه قانونی.

**مرز MVP:** دزفول، کاربران داخلی، یک کارشناس ثبت و یک کارشناس بررسی در زمان آغاز؛ بدون پورتال مالک/مجری/بازرس، کارتابل مشترک، موتور گردش کار پویا، پیامک و گزارش‌ساز پویا. تعدد کاربران در لایه داده ممنوع نمی‌شود.

**اولویت:** `P0` یعنی هسته پایه یا الزام ایمنی مسیر اول انتهابه‌انتها؛ `P1` یعنی در محدوده MVP و لازم پیش از بهره‌برداری رسمی، اما قابل اجرا پس از برش اصلی. `P1` به معنی حذف قابلیت از MVP نیست. تخمین روز/هزینه و Sprint هنوز تعیین نشده و نباید حدس زده شود.

**وضعیت اولیه تمام موارد:** `Not Started`. هر مورد فقط پس از مشاهده نتیجه واقعی و تأیید مالک محصول به `Accepted` تغییر کند؛ صرف گزارش Codex ملاک نیست.

## ۲. پیش‌نیازهای بیرونی و نقاط توقف

- **`G-LEGAL`:** مصوبات معتبر ظرفیت/صلاحیت/گروه/طبقات/جغرافیا و مستندِ آستانه آزادسازی؛ تا روشن‌شدن، فقط با داده آزمایشی و بدون نتیجه حقوقی کار شود.
- **`G-OVERRIDE`:** مرجع قانونی اختیار عبور از قواعد و فهرست قاعده‌های واقعاً قابل استثنا؛ تا آن زمان تأیید استثنایی عملیاتی نشود.
- **`G-FORM`:** قالب رسمی امضای مجری و نمونه ورودی‌های معتبر (با اطلاعات شخصی پوشیده‌شده).
- **`G-SIGN`:** سیاست اعتبار حقوقی و نگهداری همه نسخه‌های امضاشده قبلی هنگام جایگزینی فرم.
- **`G-XLS`:** نمونه و ستون‌های فایل‌های Excel و قواعد تشخیص تکرار از داده حقیقی پاک‌سازی‌شده.
- **`G-AREA`:** نمونه عددی مصوب برای اصلاح متراژ با پیشرفت، تخصیص جایگزین و ظرفیت آزادشده.
- **`G-ADJUST`:** ماتریس مجوز و مرجع تأیید انواع اصلاحات `Capacity_Movement`.
- **`G-HOST`:** انتخاب زیرساخت واقعی، سیاست نگهداری فایل/بکاپ و اعداد `RPO/RTO`.
- **`G-UAT`:** نمونه‌های پذیرش نماینده کارگروه و تأیید مراحل عملیاتی و حقوقی.

**قاعده:** استوریِ دارای گیت بیرونی را می‌توان تا لایه نمایش یا تست با داده ساختگی پیش برد؛ اما اجرای قاعده نامستند در تصمیم واقعی یا اعلام آمادگی بهره‌برداری ممنوع است.

**نکته وابستگی:** ترتیب جدول، راهنمای محصولی است نه فهرست قطعی `topological sort`؛ در هر برش پیش‌نیازهای ریز هر استوری ملاک هستند. مثلاً `REQ-08` بدون `CAP-02` انجام نمی‌شود و `REQ-07` به `DOC-02` وابسته است.

## ۵. تعریف آماده‌بودن و تعریف تکمیل

### `Definition of Ready` (پیش از آغاز هر استوری)
- ورودی، خروجی و نمونه حالت موفق/ناموفق مشخص باشد؛ وابستگی‌های داده‌ای و حقوقی بررسی شوند.
- مالک محصول بداند کدام فایل‌ها و موجودیت‌ها احتمالاً تغییر می‌کنند و چرا.
- برای استوری‌های ظرفیت و صلاحیت، قاعده و نسخه معتبر یا صریحاً «داده آزمایشی تا تعیین مستند» مشخص باشد.
- سطح دسترسی و هر اثر بر ظرفیت یا تصمیم رسمی معلوم باشد.

### `Definition of Done` (پیش از پذیرش هر استوری)
- یک قابلیت کوچک از API تا UI (اگر UI لازم است) عملاً قابل نمایش باشد؛ از ساخت جدول بدون کاربرد انتهابه‌انتها خودداری شود.
- آزمون خودکار متناسب با ریسک نوشته و اجرا شود؛ برای ظرفیت، تراکنش و هم‌زمانی، آزمون روی SQL Server واقعی ضروری است.
- اعتبارسنجی سمت سرور، مجوزدهی، لاگ خطا و نسخه هم‌زمانی رعایت شوند.
- migration قابل فهم، اسناد لازم و راه اجرای محلی به‌روزرسانی شوند؛ فایل حساس در Git قرار نگیرد.
- گزارش Codex شامل تغییر فایل‌ها، دلیل تغییر، روش آزمون، نتیجه واقعی، محدودیت‌ها و ریسک‌ها باشد.
- مالک محصول تغییر را در برنامه اجرا و رسماً قبول کند؛ **Codex اجازه commit و push خودکار بدون فرمان صریح ندارد**.

## ۶. چرخه همکاری مالک محصول و Codex

1. **تحلیل:** من هدف استوری، مفهوم فنی و معیار پذیرش را به زبان ساده شرح می‌دهم؛ شما تصمیم اجرایی را تأیید می‌کنید.
2. **بازرسی بی‌تغییر:** Codex فقط وضعیت مخزن، بسته‌ها و کد مرتبط را می‌خواند و طرح حداقلی + فایل‌های پیشنهادی را گزارش می‌کند.
3. **اجرا در محدوده یک استوری:** با اجازه شما، Codex تغییر کوچک و مشخص اعمال می‌کند؛ از ساخت ماژول‌های آینده و انتزاع اضافی پرهیز می‌کند.
4. **راستی‌آزمایی:** شما دستورات، خروجی تست، UI و مهاجرت را خودتان بررسی می‌کنید؛ خطا با همان استوری اصلاح می‌شود.
5. **ثبت:** پس از پذیرش شما، commit کوچک با ارجاع به شناسه استوری ساخته می‌شود؛ سپس استوری بعدی.

## ۷. نخستین اقدام اجرایی (فقط بررسی، بدون تغییر کد)

**استوری شروع:** `FND-01`، سپس `FND-02`. حتی اگر مخزن و SDK از قبل آماده‌اند، ابتدا وضعیت واقعی آن‌ها را بررسی می‌کنیم و کار تکراری انجام نمی‌دهیم.

**پرامپت پیشنهادی برای Codex:**

```text
در مخزن فعلی «سامانه مدیریت ارجاع کار مجریان ذی‌صلاح»، فعلاً فقط بررسی کن و هیچ فایلی را ایجاد، حذف یا تغییر نده؛ commit و push هم نکن.
هدف: اجرای استوری FND-01 و ارزیابی آمادگی FND-02. معمارى هدف: .NET 11 (net11.0), ASP.NET Core Web API, EF Core 11, SQL Server, React + TypeScript + Vite, Modular Monolith.
1) ساختار فعلی مخزن، branch، git status و فایل‌های پروژه را گزارش کن.
2) وضعیت dotnet --info و نصب SDK 11، node/npm و SQL Server (در حد دسترسی موجود) را بررسی کن. اگر دستور در محیط تو قابل اجرا نیست، صریح بگو.
3) وجود solution، API، frontend، tests، .gitignore و فایل‌های config را بررسی کن؛ هرگز رازها یا مقدار رمز/connection string را چاپ نکن.
4) فقط حداقل تغییرات پیشنهادی برای FND-02 را به تفکیک فایل و دلیل توضیح بده؛ از ایجاد چهار پروژه یا الگوهای پیچیده بدون نیاز واقعی خودداری کن.
5) خروجی را در قالب «وضعیت موجود | کمبودها | طرح کوچک پیشنهادی | دستورهای قابل اجرای دستی | ریسک‌ها» گزارش کن.
در پایان متوقف شو و برای شروع تغییر کد منتظر تأیید مالک محصول بمان.
```
